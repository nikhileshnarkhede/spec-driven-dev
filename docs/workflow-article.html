One piece at a time

Building a large ML project from one spec with Claude Code, without letting a single unchecked line onto main.

A complete spec for a real ML system runs to dozens of pages: preprocessing, models, losses, calibration, decision logic. Hand all of it to an AI assistant at once and you get a lot of code you can't easily check. The route above is the fix: cut the spec into small pieces, run each piece down the same line, and let nothing reach main without independent evidence that it does what the spec says.

Each station is a command. They all start with /dev- and carry their step number, so typing /dev- lists them in order. Every command ends by naming the next one, so you never have to remember the route. Before the first station there is /dev-spec, for when you have an idea rather than a spec; after every few pieces there is /dev-retro, which reads what the pieces cost and changes the line itself.

The spec becomes a departure board

The board records what each piece needs, so the model can't start before the data layer it consumes is finished. Pieces leave the board one at a time, in dependency order: the most independent piece first, and never a piece whose dependency carries a higher number.

Every piece gets a contract

Requirements leave choices open: which piece owns a config key, how two sections interact, what a function is called and what it raises. When the implementer, the test writer and the reviewers each settle those choices separately, every mismatch costs a whole implement, test and review round. In one measured run, every item that forced a second round, and both broken tests, came from exactly such open choices.

So the split now writes a short build contract beside each sub-spec. It records who owns what, the open questions and cross-section conflicts settled with you up front, the exact interfaces with one example call each, numbered acceptance checks with literal values, and the risks to design against. It also carries robustness checks drawn from the project's hazard register, so stale outputs, missing provenance and bad input are built with the feature rather than in a round after review. A script refuses to start a piece while anything in its contract is still undecided. Pieces are kept small, at around a dozen acceptance checks and never more than 16, because a small piece leaves fewer gaps to guess.

Two stops are yours

Look back at the map. The amber stations are where the line waits for you. At Write you approve a plan before any code exists: files, interfaces, tensor shapes, config keys, and a map from every spec statement to the code that will satisfy it. At Fix review you answer every finding with fix, accept with a reason, or reject with evidence. Every other station runs by itself.

The amber lines are the only ways back. A failing test sends the piece to Write for more code. A fix sends it back through Test and Review, because those reports described code that no longer exists. A clean review takes the express to Final.

Why the tests and reviews can be trusted

If the person who wrote the code also writes the tests, the tests check what the code does, not what it should do. So the writer agent works from the spec and the function signatures alone. The runner can execute but not edit, so a failing check can't be "fixed" by weakening it. It sorts every failure into one of five classes (not built, wrong behaviour, test defect, spec contradiction, environment), and the class decides where you go next.

The two reviewers look for different things. One holds every spec statement against the change and returns a verdict per acceptance check. The other is a senior ML reviewer hunting for the silent bugs tests rarely catch, such as data leaking between splits or dropout left on at evaluation. Both have a budget: at most ten and eight findings, and neither reports a limitation the contract already records. Across the first 25 pieces, review had been a third of all tokens, most of it spent on findings everyone already knew about.

Evidence is checked at the signal

Every report records a fingerprint of the code it checked: committed, uncommitted and new files together. Before committing, Final recomputes that fingerprint and re-runs the tests. A harmless-looking edit made after review changes the fingerprint, and the signal stays red until the reports catch up. Commit, push, merge and branch deletion each still wait for your yes, and no commit message or PR credits an AI tool.

Opus where it decides correctness

Switching models mid-session re-reads the whole conversation without the prompt cache, so the Opus steps sit where the session is still short: Spec and Split run once, and Write comes right after Select. Agents run on their own models without touching yours. Effort follows the Claude Code guidance: high where edge cases matter, low where a step is procedural, and never max, which the docs warn tends to overthink. The pipeline reviewer came down from xhigh to high after the ledger showed the deepest setting fixing 18 of 104 findings at a quarter of all tokens.

Or let it run unattended

When you'd rather not sit through steps 1 to 5, /dev-auto NN runs them for you in up to three rounds. An implementer agent builds the piece, the same independent tests and reviewers check it, and the command decides each finding by fixed rules: confirmed bugs of medium severity or worse are fixed, minor ones are fixed or accepted with a reason, and false alarms are rejected with evidence. Open questions get the reading most faithful to the spec, logged as an assumption for you to confirm.

All three rounds run on Sonnet unless round 2 leaves failing checks or confirmed defects; only then does round 3 switch to Opus at its deepest setting, with at most five items per launch. Hardening the reviewers suggest beyond the contract isn't fixed round by round: it is collected and offered to you once, at the end, and anything the hazard register should have covered is noted for the next retro. Later rounds use a focused re-review that checks the fixes and the changed code, not the whole change again. A hook stops the implementer from touching the independent tests, the run refuses to start while the contract has an open decision, because that decision is yours, and it refuses a session that already carries other work, because every one of its own calls re-reads the whole conversation. The run ends at Ready for Final with a short audit of every decision it made on your behalf.

The line keeps its own log

Every finished piece leaves a row: how many rounds it took, how its first independent test run went, why each extra round happened, and what every agent cost. The first 25 pieces taught three things. Once contracts existed, verification was nearly one-pass; the extra rounds came from review findings and from a hardening round chosen after review almost every time; and three oversized pieces took a third of all tokens. The rules in this article (robustness checks in the contract, reviewer budgets, the hard size cap, dependency-ordered numbering) came out of that record, and /dev-retro is how the next ones will.

Small pieces, independent evidence, and a written answer for every finding. Slower per line than "just generate it", and far faster per line you can trust.
